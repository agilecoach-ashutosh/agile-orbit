PRACTICAL WORKFLOWS

What connected product delivery can look like

PRODUCT INSIGHT → DELIVERY

Turn behaviour into a backlog hypothesis

Amplitude → Notion / Slack → Jira / Linear

Ask why activation or retention changed, bring supporting research and conversations into context, then draft a candidate work item. Keep prioritisation and product decisions human-owned.

DESIGN → CODE → API TEST

Carry intent through implementation

Figma → GitHub / GitLab → Postman

Pull design-system context into the coding agent, implement against the actual repository, then create or run API checks from the same working context rather than recreating requirements by hand.

INCIDENT → FIX → FOLLOW-UP

Shorten the evidence loop

Sentry / Datadog → GitHub → Jira

Use production evidence to understand the failure, inspect relevant code, prepare a change and create follow-up work. Production actions and incident command remain explicitly controlled.

EXAMPLE

Delivery Health Agent

Jira / Linear contributes work state, aging, dependencies and planned outcomes. GitHub / GitLab contributes engineering change and CI evidence. Sentry / Datadog contributes runtime signals. Amplitude contributes product behaviour. The agent can summarize delivery risk and missing evidence—but should not infer causation merely because two signals correlate.

PERMISSION DESIGN

Connect in layers, not all at once

LEVEL 1

🟢 Read context

  • Search documentation
  • Read issues / designs / code
  • Query dashboards or telemetry
  • Summarize evidence

Best place to start.

LEVEL 2

🟡 Draft / update

  • Draft Jira or Linear work
  • Create documentation
  • Update comments or metadata
  • Create test collections/specs

Require clear scope and review.

LEVEL 3

🔴 Execute / change

  • Modify source code
  • Trigger workflows
  • Change production-facing state
  • Take irreversible actions

Use explicit human checkpoints and rollback.

CHECK BEFORE CONNECTING

Six questions before enabling any MCP server

Is it the official server?

Verify the vendor domain, repository and documentation. Do not trust a connector simply because the name matches a popular product.

What can it read?

Repositories, tickets, conversations, files, customer data, analytics or production logs?

What can it write?

Comments, issues, code, dashboards, designs, records or external messages?

What can it execute?

Tests, workflows, deployment operations, API calls or other actions?

Can the scope be reduced?

Prefer read-only modes, selected toolsets, project-level constraints and least-privilege OAuth scopes.

Where is human approval?

Define the checkpoint before customer-facing, production, money, identity, compliance or destructive actions.
