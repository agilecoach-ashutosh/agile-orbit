Definition of Done Generator

Turn your team's real technology and delivery context into a practical starting point for a Definition of Done.

PURPOSE

Why use this prompt?

Use AI to quickly create a team-specific Definition of Done instead of starting with a generic checklist. Give AI enough context about what the team builds, the type of work it delivers, its technology, flow, testing, release and operational expectations, then let it identify what should be true before work is considered Done.

COPY-READY PROMPT

Prompt

AGILE ORBIT / PROMPT
ROLE:
Act as an experienced Agile Coach and software delivery practitioner.

OBJECTIVE:
Create a practical, team-specific Definition of Done (DoD) based on the team's real product, technology and delivery context.

The goal is to give the team a strong starting point based on how they actually build, test, integrate, release and operate software — not a generic Scrum checklist.

TEAM CONTEXT:

1. What does your team build?
Describe the product, application, service or platform.
{{TEAM_PRODUCT}}

2. What kind of work does the team usually deliver?
Examples: UI features, APIs, backend services, data pipelines, integrations, infrastructure, configuration, technical improvements or bug fixes.
{{TYPICAL_WORK}}

3. What is your technology stack?
Include languages, frameworks, databases, cloud/platform and important technologies where relevant.
{{TECH_STACK}}

4. How does it broadly work?
Give a simple 1–3 line application or data flow.
Example: Mobile App → API Gateway → Service → Database → External Banking System
{{HIGH_LEVEL_FLOW}}

5. How do you test and release?
Describe testing practices, CI/CD, environments, deployment and release approach.
{{TESTING_RELEASE}}

6. What quality, security, compliance or operational requirements matter?
Examples: security scanning, audit logging, accessibility, performance, monitoring, alerting, rollback, regulatory or data requirements.
{{SPECIAL_REQUIREMENTS}}

7. Think about your last successfully delivered story.
What exactly had to happen before your team considered it Done? Describe the real steps or conditions, even if they are informal.
{{LAST_SUCCESSFULLY_DELIVERED_STORY}}

ANALYZE:
Use the context above to determine what should be true before a backlog item can genuinely be considered Done for this team.

Consider only areas relevant to the team, including:
- Acceptance criteria and business validation
- Development completion and code review
- Code quality and maintainability
- Unit, integration, functional and regression testing
- API, integration and data validation
- Security and compliance
- Performance and accessibility where relevant
- CI/CD and deployment
- Monitoring, logging and production readiness
- Documentation and operational readiness

RULES:
- Do not give a generic Scrum or textbook DoD.
- Do not invent tools, processes, regulations, environments or policies that were not provided.
- Use the team's actual context to decide which criteria are relevant.
- Make every criterion observable and verifiable.
- Focus on outcomes and quality conditions, not activities for their own sake.
- Keep the DoD practical and achievable for the team.
- If something may be important but the information is missing, mark it as “Consider” rather than making it mandatory.
- Identify conditional criteria for changes such as database, API, integration, security, infrastructure or configuration changes.
- Distinguish between criteria that apply to every item and criteria that apply only to certain types of work.
- Do not turn the DoD into a detailed test plan, release procedure or process manual.
- Prefer evidence that a team could realistically inspect or demonstrate.

OUTPUT:

1. PROPOSED DEFINITION OF DONE
Create approximately 10–15 practical criteria grouped into relevant categories. For each criterion, explain briefly why it matters for this team.

2. CONDITIONAL CRITERIA
List criteria that apply only when specific types of changes are made, such as database, API, integration, security, infrastructure, data or configuration changes.

3. NON-NEGOTIABLES
Identify the 5–10 criteria that should never be skipped for this team.

4. GAPS / QUESTIONS
Identify important areas where more team information is needed. Do not guess the answer.

5. RECOMMENDED TEAM DOD
Provide a clean final checklist of approximately 10–15 items that the team can take into a discussion and refine.

6. WHAT CHANGED FROM THE TEAM'S CURRENT PRACTICE
If the “last successfully delivered story” reveals practices that are missing from the proposed DoD, highlight them so the team can decide whether to formalize them.

IMPORTANT:
This is a proposed Definition of Done, not an authoritative or official Scrum requirement. The team should review, modify and agree on the final DoD before adopting it.

The purpose is to make the DoD creation exercise faster and more evidence-based — not to replace team agreement.

EXAMPLE INPUT:

Team builds:
Digital banking APIs and backend services for account balances, transfers and payments.

Typical work:
REST APIs, business logic, database changes, third-party integrations and production fixes.

Technology stack:
Java, Spring Boot, PostgreSQL, AWS and Kafka.

High-level flow:
Mobile App → API Gateway → Spring Boot Service → PostgreSQL / Kafka → External Banking Systems

Testing and release:
Unit and integration tests, API testing, automated CI pipeline, QA environment and production deployment through CI/CD.

Special requirements:
Security scanning, audit logging, performance expectations and production monitoring.

Last successfully delivered story:
Before we called it Done, the code was reviewed, automated tests passed, QA verified it, the API was deployed to the test environment, monitoring and logging were checked, and the Product Owner accepted the story.

EXAMPLE OUTPUT DIRECTION:
The resulting DoD should reflect this team's actual delivery context. For example, it may include acceptance confirmed, code reviewed, relevant automated tests passing, integration/API behavior verified, security checks completed where applicable, deployability demonstrated, required monitoring/logging in place and operational documentation updated where needed. Do not copy these examples blindly; derive the final criteria from the team's inputs.

Facilitation Tip

Copy the prompt as-is, then replace the input placeholders with your team's context. You can use the example as a model for the level of detail to provide.

✦
Facilitation Tip

Don't ask the team to approve the AI output immediately. Ask: “What is missing here that would make us uncomfortable calling a story Done?” Use the answers to refine the final DoD together.
