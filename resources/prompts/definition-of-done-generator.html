Definition of Done Generator

Turn your team's real technology and delivery context into a practical starting point for a Definition of Done.

PURPOSE

Why use this prompt?

Use AI to quickly create a team-specific Definition of Done instead of starting with a generic checklist. Give AI enough context about what the team builds, the type of work it delivers, its technology, flow, testing, release and operational expectations, then let it identify what should be true before work is considered Done.

INPUT EXAMPLES

What good inputs can look like

Use these realistic banking examples as a guide. Replace them with your team's actual context; they are examples, not mandatory requirements.

1. What does your team build?

A digital banking platform that provides account management, payments, fund transfers and customer transaction history.

2. What kind of work does the team usually deliver?

REST APIs for payment processing, backend services for account validation, database changes, third-party payment integrations and production defect fixes.

3. What is your technology stack?

Java, Spring Boot, PostgreSQL, Kafka, AWS, REST APIs and GitHub Actions for CI/CD.

4. How does it broadly work?

Mobile App → API Gateway → Payment Service → PostgreSQL / Kafka → External Banking System.

5. How do you test and release?

Developers perform unit testing, automated integration tests run in CI, QA validates functionality in a test environment, security scans run in the pipeline, and approved changes are deployed to production through CI/CD.

6. What quality, security, compliance or operational requirements matter?

Customer and transaction data must be protected, audit logging is required for financial transactions, security vulnerabilities must be addressed, production services require monitoring and alerts, and changes must comply with applicable banking policies.

7. Think about your last successfully delivered story.

For the last payment API story, code review was completed, unit and integration tests passed, QA validated the transaction flow, security scanning had no unresolved critical issues, the API was deployed to the test environment, logging and monitoring were verified, and the Product Owner accepted the story.

COPY-READY PROMPT

Prompt

AGILE ORBIT / PROMPT
ROLE:
Act as an experienced Agile Coach and software delivery practitioner.

OBJECTIVE:
Create a practical, team-specific Definition of Done (DoD) based on the team's real product, technology, quality and delivery context.

The goal is to help the team define what must be true before a backlog item can genuinely be considered Done — based on how the team actually builds, tests, integrates, releases and operates software.

Do not produce a generic Scrum or textbook Definition of Done.

TEAM CONTEXT:

1. What does your team build?
Describe the product, application, service or platform.
{{TEAM_PRODUCT}}

2. What kind of work does the team usually deliver?
Examples may include UI features, APIs, backend services, data pipelines, integrations, infrastructure, configuration, technical improvements or bug fixes.
{{TYPICAL_WORK}}

3. What is your technology stack?
Include languages, frameworks, databases, cloud/platform and other important technologies where relevant.
{{TECH_STACK}}

4. How does it broadly work?
Give a simple 1–3 line application or data flow.
{{HIGH_LEVEL_FLOW}}

5. How do you test and release?
Describe your testing approach, environments, CI/CD, deployment and release practices.
{{TESTING_RELEASE}}

6. What quality, security, compliance or operational requirements matter?
Include anything important such as security scanning, audit logging, accessibility, performance, monitoring, alerting, rollback, regulatory or data requirements.
{{SPECIAL_REQUIREMENTS}}

7. Think about your last successfully delivered story.
What exactly had to happen before your team considered it Done? Describe the real conditions or practices, even if they were informal.
{{LAST_SUCCESSFULLY_DELIVERED_STORY}}

ANALYZE THE TEAM CONTEXT:
Use the information provided above to determine what should be true before a backlog item can genuinely be considered Done for this team.

Consider only areas relevant to the team's context, including:
- Acceptance criteria and business validation
- Development completion and code review
- Code quality and maintainability
- Relevant automated and manual testing
- API, integration and data validation
- Security and compliance
- Performance and accessibility where relevant
- CI/CD and deployment readiness
- Monitoring, logging and production readiness
- Documentation and operational readiness

RULES:
- Do not provide a generic Scrum or textbook DoD.
- Do not invent tools, processes, regulations, environments or policies.
- Use the team's actual context to determine relevance.
- Make every criterion observable and verifiable.
- Focus on outcomes and quality conditions rather than activities for their own sake.
- Keep the DoD practical and achievable.
- Do not make assumptions when important information is missing.
- If something may be important but the information is insufficient, mark it as “Consider”.
- Distinguish criteria that apply to every backlog item from criteria that apply only to specific types of work.
- Identify conditional criteria for database, API, integration, security, infrastructure, data or configuration changes where relevant.
- Prefer evidence that the team could realistically inspect, demonstrate or verify.
- Do not turn the DoD into a detailed test plan, release procedure or process manual.
- Avoid unnecessary criteria simply to make the checklist look comprehensive.
- Prioritize the smallest set of criteria that provides confidence that the work is genuinely Done.

OUTPUT:

1. PROPOSED DEFINITION OF DONE
Create approximately 10–15 practical criteria grouped into relevant categories.

For each criterion provide:
- The DoD criterion
- A brief explanation of why it matters for this team

2. CONDITIONAL CRITERIA
List criteria that apply only when specific types of changes are made, such as:
- Database changes
- API changes
- Integration changes
- Security-sensitive changes
- Infrastructure changes
- Data changes
- Configuration changes

Only include categories relevant to the team's context.

3. NON-NEGOTIABLES
Identify the 5–10 criteria that should never be skipped for this team.

4. GAPS / QUESTIONS
Identify important areas where the team's information is insufficient to confidently define the DoD.

Do not guess the answers.

5. RECOMMENDED TEAM DOD
Create a clean, concise final checklist of approximately 10–15 items that the team can take into a discussion and refine.

Write these as clear, observable statements rather than vague activities.

6. WHAT CHANGED FROM CURRENT PRACTICE
Compare the proposed DoD with the team's description of its last successfully delivered story.

Highlight:
- Practices the team already follows but has not formally captured
- Important criteria that appear to be missing
- Practices that may need clarification before becoming part of the DoD

IMPORTANT:
This is a proposed Definition of Done, not an authoritative or official Scrum requirement.

The team should review, modify and agree on the final DoD before adopting it.

The purpose of this exercise is to make DoD creation faster, more practical and evidence-based — not to replace team discussion or agreement.

Copy the prompt as-is, then replace the input placeholders with your team's context. Use the input examples above as a guide for the level of detail.

✦
Facilitation Tip

Don't ask the team to approve the AI output immediately. Ask: “What is missing here that would make us uncomfortable calling a story Done?” Use the answers to refine the final DoD together.
