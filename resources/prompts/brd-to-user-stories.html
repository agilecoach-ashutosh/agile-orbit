BRD to Sprint-Ready User Stories

Transform a Business Requirements Document into granular, independently deliverable Agile user stories.

Product Owner / Business AnalystBacklog RefinementExtract + Decompose
PURPOSE

Why use this prompt?

Analyze a BRD for functional requirements, behaviors, business rules, validations, errors, data, roles and edge cases, then split the requirements into small vertical slices suitable for a Scrum backlog.

COPY-READY PROMPT

Prompt

AGILE ORBIT / PROMPT
You will be given a Business Requirements Document (BRD).

Your objective is to convert the BRD into a set of extremely granular, sprint-ready Agile user stories.

Think and behave like an experienced Product Owner preparing backlog items for a Scrum team.

--------------------------------------------------
STEP 1 — ANALYZE THE BRD
--------------------------------------------------

Carefully read and analyze the entire BRD.

Extract:
• Functional requirements
• User interactions
• System behaviors
• Business rules
• Validation rules
• Error conditions
• Data requirements
• Role-based behaviors
• Alternate flows
• Edge cases

Do NOT invent requirements that do not exist in the BRD.

When providing detailed description, you MUST extract the wording **exactly from the BRD** wherever possible.

Do not paraphrase BRD content for the description section.

--------------------------------------------------
STEP 2 — SPLIT INTO SMALL USER STORIES
--------------------------------------------------

Break requirements into the **smallest independently deliverable user stories**.

Stories should ideally be completable within **1–3 days of development effort**.

Apply user story splitting patterns from the Humanizing Work Guide where appropriate:

• Workflow Steps  
• Operations / CRUD  
• Business Rule Variations  
• Data Variations  
• Data Entry Methods  
• Major Effort (build minimal first, extend later)  
• Simple vs Complex (core first, edge cases later)  
• Defer Performance / Non-Functional Requirements  
• Break Out a Spike (for research)

Also split when meaningful for:

• Happy paths  
• Alternate flows  
• Edge cases  
• Validation rules  
• Error handling  
• Role-based permissions  
• Business rule variations  
• Data variations  

Every story must:

• Follow INVEST principles  
• Deliver observable value  
• Be independently testable  
• Represent a vertical slice of functionality  

Prefer **smaller stories over larger stories**.

--------------------------------------------------
STEP 3 — USER STORY FORMAT (STRICT)
--------------------------------------------------

The Excel output must contain a column named:

**User Story**

This column must contain the following sections **inside the SAME CELL**.

The content MUST strictly follow this Markdown structure:

`As a` [type of user]

`I want to` [perform an action]

`So that` [benefit/value]


**Detailed Description**

[Insert detailed context extracted directly from the BRD using the original wording wherever possible. This section should provide sufficient context about the requirement, workflow, rules, or system behavior.]


**Acceptance Criteria**

- [ ] Criteria one
- [ ] Criteria two
- [ ] Criteria three

Acceptance criteria must:

• Not use BDD (Given/When/Then)  
• Be testable and observable  
• Describe system behavior  
• Cover validations, constraints, system responses  
• Include happy path and relevant edge cases  
• Be written as checklist items exactly as shown above

--------------------------------------------------
STEP 4 — EXCEL OUTPUT FORMAT
--------------------------------------------------

Generate the final output as an **Excel file (.xlsx)**.

The Excel file must contain ONLY these columns:

1. Title  
2. User Story  
3. Explanation of Split  

Column rules:

Title
• Short descriptive name for the story

User Story
• Must contain the entire Markdown structure described above
• Value statement, description, and acceptance criteria MUST all be inside the SAME CELL

Explanation of Split
Explain:

• Splitting pattern used  
• Why the requirement was split this way  
• Why the story is independently testable  

--------------------------------------------------
EXCEL FORMATTING RULES
--------------------------------------------------

• Each row must represent exactly ONE user story  
• Do NOT merge cells  
• Do NOT create additional columns  
• Do NOT output anything outside the table  
• Acceptance criteria must appear as checklist items using "- [ ]"  
• Preserve line breaks inside the User Story cell  

--------------------------------------------------
QUALITY EXPECTATIONS
--------------------------------------------------

User stories must be:

• Clear
• Testable
• Developer-ready
• Small enough for a sprint
• Written with meaningful user value

Do not combine multiple behaviors into one story.

--------------------------------------------------
FINAL INSTRUCTION
--------------------------------------------------

After analyzing the BRD, generate the Excel table according to the exact structure defined above.

Copy the prompt as-is, then replace the input placeholders with your own context.

✦
Quality Guardrail

The prompt emphasizes extracting wording from the BRD wherever possible and avoiding invented requirements. Validate the generated stories against the source document before using them in the backlog.
