Story → Visual Flow

Turn requirements into Mermaid diagrams for faster backlog refinement.

PURPOSE

Why use this prompt?

Turn a user story, use case, or acceptance criteria into a discussion-ready flow that shows user actions, system responses, decisions and stated exceptions. Surface gaps without inventing requirements.

COPY-READY PROMPT

Prompt

AGILE ORBIT / PROMPT
Act as an experienced Business Analyst supporting a backlog refinement session.

I will provide a user story, use case, requirement, acceptance criteria, or feature description.

Convert the requirement into a clear Mermaid flowchart that I can paste into a Mermaid editor and use to explain the story visually to the delivery team.

INPUT:
[PASTE USER STORY / USE CASE / ACCEPTANCE CRITERIA HERE]

ANALYZE:
Identify, where stated, the actor, trigger, user actions, system actions, business rules, validations, decision points, happy path, alternate paths, exception paths, end states, and external-system interactions.

RULES:
1. Do not invent requirements, actors, business rules, validations, or failure paths.
2. If something important is unclear, flag it as "TBD / Clarification Needed" in Refinement Questions. Add a TBD node only where the supplied flow cannot proceed without that clarification; do not guess its branches.
3. Focus on behavior and flow. Include implementation details only when explicitly provided.
4. Distinguish actions with short labels such as "User: Submit request" and "System: Display confirmation". Use the actual actor name where available.
5. Combine related steps; do not create one node for every sentence. Keep labels short and understandable to business and technical team members.
6. Use decision diamonds only when the requirement genuinely branches. Label each branch with Yes / No or the stated outcome.
7. Include alternate and failure paths only when supplied. Raise missing exception behavior as a refinement question.
8. Use simple, widely supported Mermaid syntax: flowchart TD, rectangles, decision diamonds, and labeled arrows.
9. Use simple unique node IDs and double-quoted labels. Avoid experimental syntax, icons, plugins, HTML labels, and custom styling.
10. Check that every edge references a defined node and that the diagram matches the input. Split a large flow into smaller named diagrams if readability requires it.

SYNTAX EXAMPLE (illustrates syntax only; do not add these requirements to my story):
flowchart TD
    A["User: Submit request"] --> B{"System: Request valid?"}
    B -->|Yes| C["System: Confirm request"]
    B -->|No| D["System: Show validation errors"]

OUTPUT FORMAT:

Story Flow Summary:
A maximum of 5 short bullets explaining the journey.

Mermaid Diagram:
Provide the diagram in a fenced mermaid code block, starting with flowchart TD.

Refinement Questions:
List only important gaps, ambiguities, edge cases, or decisions to clarify. If none are identified, say "No clarification gaps identified in the supplied requirement."

The diagram should help a BA or Product Owner walk the team through the requirement from start to finish during backlog refinement.

Copy the prompt as-is, then replace the input placeholders with your own context.

HOW TO USE

From story to team conversation

  1. Copy the prompt into your AI assistant and replace the input placeholder with your story and acceptance criteria.
  2. Copy only the generated Mermaid code, without the code fences, into Mermaid Live Editor.
  3. Review the flow against the requirement, then share or export the diagram for refinement.
✦
Facilitation Tip

Walk the team through the happy path, then the decisions and exceptions. Resolve the refinement questions together before treating the diagram as agreed behavior.
