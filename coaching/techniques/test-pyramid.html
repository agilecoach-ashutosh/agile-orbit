Test Pyramid

A testing heuristic that favours many fast lower-level automated tests and fewer slower broad-stack or UI tests.

TECHNOLOGYBUILT-IN QUALITYRESEARCHED METHOD
← Back to Built-in QualityUnderstand the method ↓
Core idea: Create fast, reliable feedback without depending on a large brittle end-to-end suite.

Understand the method first

Many · fast · focused

Unit tests

Exercise small pieces of behaviour quickly and provide rapid feedback close to the code.

Some

Service / integration tests

Check collaboration across meaningful boundaries without always driving the full user interface.

Fewer · slower

UI / end-to-end tests

Protect critical journeys that genuinely require broad-stack verification.

Lineage: Mike Cohn introduced the Test Pyramid in Succeeding with Agile; Martin Fowler later popularised and discussed the heuristic.

How to use it

  1. Map the current automated-test portfolio by level and feedback time.
  2. Find where slow or brittle tests dominate the feedback cycle.
  3. Move checks closer to the code/service boundary where that gives equivalent confidence.
  4. Keep a small set of valuable end-to-end tests for cross-system behaviour.
  5. Track reliability and speed, not just test counts.

Coach with it

Use the method as a lens for inquiry, not as a rigid prescription. Useful coaching questions include:

“Where do we first learn a change is unsafe?”

“Which UI tests could be replaced by faster lower-level feedback?”

“What risk genuinely requires an end-to-end check?”

“Are flaky tests teaching the team to ignore feedback?”

Agile example

Business rules are verified mainly at unit/service level while a smaller UI suite covers only critical customer journeys.

Watch for

Watch for

The pyramid is a heuristic, not a mandated ratio.

Watch for

Modern architectures may use different test shapes; optimise for trustworthy, fast feedback.
