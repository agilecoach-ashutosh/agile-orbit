Test-Driven Development (TDD)

A development technique that repeatedly cycles through a failing test, the simplest passing implementation and refactoring.

TECHNOLOGYBUILT-IN QUALITYRESEARCHED METHOD
← Back to Built-in QualityUnderstand the method ↓
Core idea: Use executable feedback to shape behaviour and design in small increments.
RED — failing test→GREEN — make it pass→REFACTOR — improve design→Repeat

Understand the method first

This method is best understood as a whole rather than as separate components.

Lineage: Kent Beck developed and popularised modern TDD through Extreme Programming. The cycle is commonly summarised as Red → Green → Refactor.

How to use it

  1. Choose the next small behaviour to add.
  2. Write a test that fails for the right reason.
  3. Write the simplest implementation that makes the test pass.
  4. Refactor code and tests while preserving behaviour.
  5. Repeat in small increments and keep the feedback loop fast.

Coach with it

Use the method as a lens for inquiry, not as a rigid prescription. Useful coaching questions include:

“What is the next smallest behaviour we need?”

“Did the test fail for the reason we expected?”

“What design pressure is the test revealing?”

“Can we refactor safely while the feedback remains green?”

Agile example

Before implementing a new risk-rule edge case, the developer writes one failing example, makes it pass, then improves the design before moving to the next case.

Watch for

Watch for

TDD is not merely “write tests before code”; the design feedback loop matters.

Watch for

A slow or unreliable test suite destroys the short cycle TDD depends on.
