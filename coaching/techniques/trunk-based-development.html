Trunk-Based Development

Developers integrate small changes into a shared mainline frequently, typically at least daily, using very short-lived branches where branches are used.

TECHNOLOGYSMALL BATCHES & CONTINUOUS INTEGRATIONRESEARCHED METHOD
← Back to Small Batches & Continuous IntegrationUnderstand the method ↓
Core idea: Reduce merge risk, branch divergence and late integration surprises.
Small change→Fast tests→Merge to trunk→Repeat frequently

Understand the method first

This method is best understood as a whole rather than as separate components.

Lineage: DORA identifies trunk-based development as a technical capability associated with continuous delivery and describes short-lived branches and frequent merging.

How to use it

  1. Measure current branch lifetime and merge frequency.
  2. Reduce the size of changes so integration can happen safely every day.
  3. Strengthen fast automated feedback on every integration.
  4. Use feature flags or other techniques when incomplete functionality must remain hidden.
  5. Track merge conflicts, code freezes and review delay as system signals.

Coach with it

Use the method as a lens for inquiry, not as a rigid prescription. Useful coaching questions include:

“How long can code diverge before risk becomes visible?”

“What prevents us from integrating today?”

“Are review queues creating de facto long-lived branches?”

“Which tests must become faster for frequent integration to be safe?”

Agile example

A team moves from multi-week feature branches to changes merged daily behind feature flags, cutting merge conflict and integration delay.

Watch for

Watch for

Trunk-based development without trustworthy automated feedback can create different risks.

Watch for

Do not optimise merge frequency while allowing review or deployment queues to grow elsewhere.
