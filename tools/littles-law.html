Little's Law Flow Calculator

THE RELATIONSHIP

Three flow measures. One simple law.

WIP = Throughput × Cycle Time

Little's Law connects the average amount of work inside a system, the average time each item spends in that system, and the average rate at which items leave it.

Work in ProgressAverage items inside the workflow
=
ThroughputItems completed per time period
×
Cycle TimeAverage elapsed time per item
Example: 20 items of average WIP ÷ 5 days average Cycle Time = 4 items/day average Throughput.

WHERE DO THE NUMBERS COME FROM?

Use consistent workflow boundaries and historical averages

Average WIP

Look at the average number of items between your agreed started and finished states — for example Development → Review → Test → Done.

Average Cycle Time

Measure elapsed time from when an item enters the selected workflow boundary until it exits that same boundary.

Average Throughput

Count completed work items over a consistent period. Example: 42 items completed over 14 days = 3 items/day.

Common sources: Jira, Azure DevOps, your Kanban board, cumulative flow diagrams and delivery analytics. Prefer averages taken over a representative historical period.
DEVELOPER CONNECTION

Little's Law also appears in the world of Java Executors

Tasks in system = Throughput × Time in system

Java's Executor / ThreadPoolExecutor does not implement Little's Law as an algorithm. But the same relationship is useful when reasoning about a thread pool as a flow system.

Incoming tasksRequests arrive at some rate.
Work queueTasks wait when workers are busy.
Worker threadsThreads execute available tasks.
CompletedFinished tasks become throughput.
WIP / L

Average tasks inside the executor system: tasks currently running + tasks waiting in the queue.

Throughput / λ

Average tasks completed per second, minute or other consistent time unit.

Time in system / W

Average queue waiting time + execution time from admission until completion.

Average tasks in system = task throughput × average time in system
20 tasks ≈ 100 tasks/sec × 0.20 sec
Why this is useful: if the executor completes about 100 tasks/second and tasks spend about 0.20 seconds from admission to completion, Little's Law implies roughly 20 tasks are in the system on average. If work arrives faster than available service capacity for a sustained period, the queue grows and latency rises.
Important: this is a way to reason about observed averages — not a formula for choosing Java's exact corePoolSize, maximumPoolSize or queue capacity. Thread-pool sizing also depends on CPU vs blocking work, variability, resource limits and workload characteristics.
WHEN TO USE

Use it to improve flow conversations

Useful during Flow Reviews, retrospectives, delivery forecasting, WIP-limit conversations and Kanban system reviews — especially when exploring how to improve delivery without simply starting more work.

Assumptions: Little's Law is most meaningful when the observed system is reasonably stable, the same workflow boundaries are used for all three measures, and averages are taken over a representative period. Treat major scope, staffing or workflow changes carefully.
